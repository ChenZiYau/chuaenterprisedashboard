### Critical unresolved database access finding

`properties`, `units`, `tenants`, `revenue` and `expenses` have RLS enabled, but each has `anon read` and `anon write` policies granting unconditional access to `anon` and `authenticated`, plus an unrestricted authenticated policy. Read-only `has_table_privilege` checks confirmed anon SELECT, INSERT, UPDATE and DELETE privileges on all five tables. The application cookie gate cannot protect direct Supabase Data API access under these policies.

The prepared migration drops these permissive policies while retaining RLS. The dashboard's server-only service-role client and scheduled service-role database check retain access. Other applications using anon/authenticated keys could lose access. The user explicitly requested **prepare for review only**, so the live policies are unchanged. Confirm other consumers before applying, then verify denied public reads/writes and retained dashboard access. The migration was not run or integration-tested against production.

## E. Remaining issues and required settings

1. **Critical: public database policies remain permissive**, per the user's review-only instruction above.
2. **Concurrent revenue creation:** no unique `(unit_id, month, year)` constraint exists. Simultaneous requests can still insert duplicates. A database constraint and atomic upsert require a reviewed migration and a non-destructive plan for any existing duplicates.
3. **Multi-request atomicity:** property reconciliation/deletion and tenant occupancy sync span requests. Partial commits and concurrent changes remain possible. A transaction/RPC design is needed to make them atomic. Tenant routes already report secondary occupancy failures separately; property operations are not fully atomic.
4. **Historical receipts:** receipts use the current unit/tenant label; revenue has no immutable payer snapshot. Reprinting after tenant replacement can show the current occupant. A reviewed snapshot design is needed; this audit did not fabricate historical payer data or alter existing records.
5. **Accounting semantics:** invoice outstanding totals treat non-paid rows as their full charge; there is no amount-paid/balance column. Electricity uses an explicitly approximate hardcoded tariff. These calculations need confirmed business rules before being changed; no claim of current utility-tariff accuracy is made.
6. **Authentication throttle:** login throttling is per process, not shared across server instances. Database/public access restrictions must not be inferred from that throttle.
7. Maintenance has no implemented service-request/work-order backend. Building it would be a new feature.
8. Production writes, external vault writes and real concurrent-writer scenarios were not tested. Read pagination is not a transactionally frozen snapshot.

Deployment configuration: retain `SUPABASE_URL` (or the public URL fallback), `SUPABASE_SERVICE_ROLE_KEY`, and a random `SESSION_SECRET` of at least 32 characters. Keep `CRON_SECRET` configured for the keepalive HTTP endpoint. Gallery features require `NEXT_PUBLIC_VAULT_URL` and server-only `VAULT_API_KEY` (optional `VAULT_URL` overrides the server destination). GitHub scheduling continues to use its existing Supabase URL/service-role secrets. No actual environment values were modified. Deploy the code changes to activate them.
